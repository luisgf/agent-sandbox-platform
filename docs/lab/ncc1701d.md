# El host de pruebas (ncc1701d)

El servidor donde los mantenedores prueban ASP con VMs de verdad: un Ubuntu con KVM (12 CPU, 32 GB, un disco aparte para las sandboxes) que comparte Docker y nginx con otras aplicaciones. Esta página es su registro: cómo está montado, cómo se despliega en él y cómo se prueba sin romper lo que corre. **No es una guía de despliegue** (para eso, [instalar](../how-to/install.md)): los nombres, las rutas y los puertos son los de este host, y las páginas del producto no los usan.

> **No tocar:** los contenedores de Docker que no son `asp-*` y nginx son de otras aplicaciones.

## Qué corre

| Pieza | Cómo está |
|---|---|
| Plano de control | Unit `asp-control-plane.service` ([plantilla](../../scripts/systemd/asp-control-plane.service)), binario `~/src/bots/build/api`, escuchando solo en `127.0.0.1:18112`: no hay TLS ni proxy delante, así que el acceso remoto es un túnel SSH. Sus ajustes están en `/etc/asp/server.yaml` ([plantilla](../../scripts/systemd/lab/server.yaml), sin secretos); los secretos, en el `EnvironmentFile` `~/.secrets/asp-idp.env` (modo 0600: los del IdP, `ASP_BOOTSTRAP_API_KEY` y `ASP_DATABASE_URL`); lo propio del host, en los drop-ins de abajo |
| Estado del plano de control | Postgres desde el 2026-10-07 (contenedor `asp-postgres`, abajo): reiniciar el plano de control conserva sandboxes, eventos y API keys. La CA y las claves OIDC y de atestación están en `/var/lib/asp-control-plane` (el modo producción no las acepta en `/tmp`) |
| Node-agent | Unit `asp-node-agent.service` ([plantilla](../../scripts/systemd/asp-node-agent-lab.service)), `/usr/local/bin/node-agent` (de root: la unit corre como root) y sus ajustes en `/etc/asp/agent.yaml` ([plantilla](../../scripts/systemd/lab/agent.yaml), 0600). Habla con el plano de control por HTTP en loopback, sin mTLS ni enroll, y se identifica con la API key de plataforma de `~/.secrets/asp-node.key`. El plano de control le habla a su API local (`127.0.0.1:9100`) con el secreto de `/var/lib/asp/agent.token`. Firma las atestaciones con la clave del plano de control (`ASP_ATTEST_KEY=/var/lib/asp-control-plane/attest-key.pem`, en la unit). Los workspaces están en `/sandbox/workspaces/<tenant>/` |
| IdP | Un Keycloak de otra aplicación, con un realm `asp` propio: [idp-keycloak.md](idp-keycloak.md) |
| Discos de las sandboxes | `/sandbox/disks` (RAID1 de 1 TB, ext4, en `fstab`). `/var` es una partición de 2,9 GB: **no** poner allí discos de sandboxes ni imágenes |
| Kernel e imagen del guest | `/opt/sandbox/{vmlinux,rootfs.img,SHA256SUMS,image.json}` son enlaces al conjunto de `/sandbox/asp-images/current/`, que `asp image pull` instala ya comprobado, uno por versión (`/sandbox/asp-images/<versión>/`). Kernel Linux 6.18.55 con la configuración de Cloud Hypervisor y todo compilado dentro (`uname -r` en el guest dice `6.18.55-asp`) y una Debian 12 de 1536 MiB. Los anteriores (`/var/lib/asp/images/rootfs.img` y `/var/lib/asp/kernels/vmlinux`) siguen ahí para volver atrás |
| Postgres | Contenedor `asp-postgres` (postgres:18, `--restart unless-stopped`) en `127.0.0.1:5433`, datos en `/sandbox/asp-postgres`, contraseña generada en `~/.secrets/asp-postgres.env`. Otra aplicación del servidor tiene su propio Postgres en el 5432, y ASP no lo usa |

**Desde el 2026-10-08 el host corre la forma nueva**: los ajustes están en `/etc/asp/server.yaml` y `/etc/asp/agent.yaml` (bandera > entorno > fichero > valor por defecto; [el fichero de configuración](../how-to/config-file.md)), no en líneas `Environment=` ni en el `ExecStart`. `build/api --config /etc/asp/server.yaml --print-config` y `node-agent --config /etc/asp/agent.yaml --print-config` dicen cuánto vale cada ajuste y de dónde sale, y `sudo node-agent --config /etc/asp/agent.yaml --doctor` comprueba el nodo (KVM, Cloud Hypervisor, kernel e imagen contra su `SHA256SUMS`, nftables, el plano de control).

## Lo que los ajustes esperan encontrar

Se crea una vez, antes del primer arranque con la forma nueva (no lo hace ninguna unidad). Nada de esto imprime un secreto:

```bash
# La API key del nodo: el plano de control está en HTTP plano y no hay un certificado de cliente que diga quién es
(umask 077; openssl rand -base64 24 > ~/.secrets/asp-node.key)
printf 'ASP_BOOTSTRAP_API_KEY=%s\n' "$(cat ~/.secrets/asp-node.key)" >> ~/.secrets/asp-idp.env

# El secreto de la API local del agente. Lo lee el plano de control, que corre como ubuntu y no es root:
# si lo crea el agente (0600, de root), el plano de control no puede leerlo
sudo install -d -m 0755 /var/lib/asp
openssl rand -hex 32 | sudo install -m 0640 -o root -g ubuntu /dev/stdin /var/lib/asp/agent.token

# Los workspaces cuelgan de <raíz>/<tenant>/; el dueño de la carpeta es el uid con el que escribe el guest
sudo install -d -m 0755 -o ubuntu -g ubuntu /sandbox/workspaces /sandbox/workspaces/default
```

Sin la API key el nodo no se registra y el agente sale al arrancar; sin el permiso de grupo en `agent.token`, un `exec` da 502 («node-agent refused the control plane (401)»); sin la raíz de workspaces, crear una sandbox con workspace da 400.

## Los drop-ins del plano de control

Lo que es propio del host y no va en `server.yaml` (que se publica) va en `/etc/systemd/system/asp-control-plane.service.d/`; las copias están en [`ncc1701d/`](ncc1701d/):

| Drop-in | Para qué |
|---|---|
| [`local-net-dial.conf`](ncc1701d/local-net-dial.conf) | `ASP_LOCAL_NET_DIAL`: la dirección que marcan los portátiles para llegar a los túneles local-net de este nodo (en la copia, un nombre de ejemplo) |
| `postgres.conf` | Espera a Docker (`After=docker.service`, `Wants=docker.service`) y reintenta sin límite (`StartLimitIntervalSec=0`, `RestartSec=5`): al arrancar el servidor, Postgres tarda más que el plano de control. No está copiado aquí porque en el host solo lo lee root |

Hasta el 2026-10-08 había dos más: `keys.conf` (las claves fuera de `/tmp`, copiadas de las que había allí para que los tokens y los certificados de nodo siguieran valiendo) e `idle.conf` (`ASP_SANDBOX_IDLE_TIMEOUT=2h`: una sandbox sin `exec` durante dos horas se **para**, no se borra, [ADR-0012](../adr/0012-retained-disks.md)). Sus valores son ahora `ca_cert`, `ca_key`, `oidc_key`, `attest_key` y `sandbox_idle_timeout` de `server.yaml`, y los drop-ins se quitaron (están en el historial de git).

El agente tiene `After=asp-control-plane.service` y **no** `Wants=`, a propósito: arrancar o reiniciar el agente no levanta un plano de control que alguien paró, y reiniciar el plano de control no toca al agente ni a sus VMs. Si el plano de control aún no responde, el agente sale al no poder registrarse y systemd lo reintenta cada 5 s sin tope.

Tras reiniciar el servidor vuelven solos Docker, `asp-postgres`, el plano de control y el agente. Las VMs mueren con el servidor, así que las sesiones que corrían quedan `stopped` (`node_agent_restarted`) y, como las paradas, se pueden reanudar con su disco. Un reinicio de verdad del servidor no se ha probado (es un host compartido): el orden y los reintentos se han ejercitado a mano. Si el agente muere (`kill -9`), systemd lo reinicia y la limpieza (`--reap-only`) corre antes y respeta las VMs vivas.

### Alternativas que se descartaron

| Alternativa | Por qué no |
|---|---|
| Solo `scripts/run-cp-lab-idp.sh` (un runner a mano) | Muere al cerrar la sesión o reiniciar, y es fácil olvidar el entorno del IdP; sirve para depurar, no junto a la unit (mismo puerto) |
| El plano de control en `:8080` | Choca con otros servicios del host, y aísla peor el modo con IdP obligatorio |
| Los secretos en `Environment=` de la unit | Se filtran en `systemctl show` y en las copias de seguridad |

## Desplegar y volver atrás

El Go del host es más viejo que el que pide el repositorio: los binarios se compilan en local (`GOOS=linux GOARCH=amd64 CGO_ENABLED=0 go build`), se copian con `scp` a un directorio de despliegue (`~/asp-deploy-<fecha>/`, modo 0700) y se comprueba su `sha256`. El orden es el de [la guía multi-nodo](../ops-multi-node.md): **plano de control, luego nodo, luego imagen del guest**. Así se subió el 2026-10-08 a la revisión de diseño:

1. **Copias** en `~/asp-backup-<fecha>/`: `pg_dump -Fc` de la base, los binarios que se van a pisar, las unidades y sus drop-ins, `~/.secrets/asp-idp.env` y `/var/lib/asp-control-plane` (la CA y las claves: sin ellas dejan de valer los tokens y los certificados de nodo).
2. **Ensayar la migración** en un Postgres desechable (`docker run --tmpfs /var/lib/postgresql -p 127.0.0.1:55432:5432 postgres:18`): se restaura la copia y el binario nuevo arranca contra ella, en otro puerto (18113) y con los ajustes del IdP de verdad. Tiene que migrar, contestar a `/healthz`, aceptar la API key de plataforma y dejar entrar al usuario del realm. Después se borra el contenedor.
3. **Crear lo que la versión nueva espera** ([arriba](#lo-que-los-ajustes-esperan-encontrar)) y dejar los dos YAML en `/etc/asp/`, sin cargar nada todavía.
4. **Plano de control**: los binarios nuevos en `build/` (los anteriores quedan como `*.pre-<fecha>`), la unidad de la plantilla, fuera los drop-ins cuyos ajustes ya están en el YAML, `systemctl daemon-reload` y `restart asp-control-plane`. Las migraciones se aplican solas al arrancar, con un cerrojo en la base. El nodo no se toca.
5. **Node-agent**: `sudo install -o root -g root -m 0755 NUEVO /usr/local/bin/node-agent`, su unidad, `daemon-reload` y `restart asp-node-agent`. Un reinicio no para las VMs (cada una vive en su `asp-vm-<id>.service`, [ADR-0014](../adr/0014-vms-outlive-the-agent.md)): el proceso nuevo adopta las que corren (`journalctl -u asp-node-agent | grep adopted`). Esta versión confina cada VM y la corre sin privilegios ([ADR-0015](../adr/0015-unprivileged-vmm.md)), y adoptar VMs de la versión anterior no se ha probado: mira antes que no haya sesiones (`systemctl list-units 'asp-vm-*'`).
6. **Kernel e imagen del guest**, construidos en el host con el script del repositorio desde un `git worktree` limpio del commit que se despliega (el Docker del host no tiene buildx: usa el constructor clásico, y el kernel sale igual de todos modos):

   ```bash
   ASP_GUEST_VERSION=0.0.0-lab.<commit> ASP_ROOTFS_SIZE_MB=1536 scripts/build-guest-image.sh --kernel /sandbox/asp-deploy/guest-out
   # un servidor de ficheros local con los cuatro, con el nombre que llevan en una release
   # (asp-guest_<versión>_{SHA256SUMS,image.json,rootfs.img.gz,vmlinux}), y
   sudo asp image pull --version 0.0.0-lab.<commit> --base-url http://127.0.0.1:18899 --dir /sandbox/asp-images
   ```

   `asp image pull` comprueba las sumas, instala el conjunto en `/sandbox/asp-images/<versión>/`, apunta `current` y enlaza `/opt/sandbox/*`. Con una release publicada es solo `sudo asp image pull --dir /sandbox/asp-images`. Hay que reiniciar el agente para que mande las huellas nuevas al registrarse (`asp node list` muestra la de la imagen, y `--json` las dos). Una imagen anterior a un cambio del guest no lleva sus unidades nuevas hasta que se reconstruye; ext4 no tiene reflink, así que el disco de cada sandbox es una copia dispersa completa de la imagen.
7. **Comprobar**: `sudo node-agent --config /etc/asp/agent.yaml --doctor` (todo `ok`) y la vida de una sandbox de verdad contra el despliegue, desde el propio host:

   ```bash
   sudo install -d -o 1000 -g 1000 /sandbox/workspaces/default/e2e
   echo host-file | sudo -u '#1000' tee /sandbox/workspaces/default/e2e/host.txt >/dev/null   # lo que la sandbox tiene que ver
   ASP_E2E_CONTROL_PLANE_URL=http://127.0.0.1:18112 ASP_E2E_WORKSPACE=/sandbox/workspaces/default/e2e \
   ASP_E2E_BIN=$HOME/src/bots/build scripts/e2e-kvm.sh        # termina con «OK e2e-kvm»
   ```

**Volver atrás.** Las copias del despliegue del 2026-10-08 están en `~/asp-backup-20261008/`. El plano de control y el agente nuevos van juntos: el primero exige al nodo una credencial que el agente anterior no manda, así que se restauran los dos o ninguno.

- *Plano de control*: `cp -p api.pre-<fecha> api && cp -p asp.pre-<fecha> asp` en `~/src/bots/build`; la unidad y los drop-ins de `units/` de la copia a `/etc/systemd/system/`; `daemon-reload` y `restart`. Una migración solo añade, así que el binario anterior arranca sobre la base nueva. Para la base de antes: con el plano de control parado, `pg_restore --clean --no-owner` del `asp.dump`.
- *Node-agent*: `bin/node-agent.before-cutover` de la copia a `/usr/local/bin/node-agent`, la unidad anterior y `restart`.
- *Imagen*: `sudo ln -sfn /var/lib/asp/images/rootfs.img /opt/sandbox/rootfs.img`, lo mismo con `/var/lib/asp/kernels/vmlinux` y `/opt/sandbox/vmlinux`, y `sudo rm /opt/sandbox/SHA256SUMS /opt/sandbox/image.json`. Las sumas de los dos ficheros están en `old-image.sha256sum`. Reiniciar el agente.

Parar todas las VMs del nodo a mano: `sudo systemctl stop asp-vms.slice`.

## Postgres

Cómo se montó el 2026-10-07, con la contraseña generada en el momento y sin imprimirla (la guía general, sin los nombres de este host, es [instalar el plano de control](../how-to/install-control-plane.md#1-la-base-de-datos)):

```bash
sudo install -d -o 999 -g 999 -m 700 /sandbox/asp-postgres        # datos fuera de /var (2,9 GB)
umask 077
printf 'POSTGRES_USER=asp\nPOSTGRES_DB=asp\nPOSTGRES_PASSWORD=%s\n' "$(openssl rand -hex 24)" > ~/.secrets/asp-postgres.env
docker run -d --name asp-postgres --restart unless-stopped --env-file ~/.secrets/asp-postgres.env \
  -p 127.0.0.1:5433:5432 -v /sandbox/asp-postgres:/var/lib/postgresql --memory 2g \
  --log-opt max-size=10m --log-opt max-file=3 postgres:18
```

`ASP_DATABASE_URL` (`postgres://asp:<contraseña>@127.0.0.1:5433/asp?sslmode=disable`) va en `~/.secrets/asp-idp.env`, nunca en la unit ni en el repositorio. Se consulta con `docker exec asp-postgres psql -U asp -d asp -Atc "select …"` (por el socket, sin contraseña). Antes de desplegar migraciones nuevas, `pg_dump` a `~/asp-backup-<fecha>/`.

## Probar sin tocar lo que corre

- **Otro plano de control** en `127.0.0.1:18113`: con `ASP_INSECURE_OPEN_API=1` para probar sin IdP, o con `ASP_IDP_ISSUER` / `ASP_IDP_JWKS_URL` apuntando a un JWKS local (`python3 -m http.server`) y tokens RS256 firmados con `openssl dgst -sha256 -sign`, que además deja probar los roles (ninguna cuenta del realm es operador ni administrador). Borrar la clave y los tokens al terminar.
- **Un Postgres desechable**: un contenedor `postgres:18` en `127.0.0.1:55432` con `--tmpfs /var/lib/postgresql`, que se borra después.
- **Los temporizadores de verdad, en corto**: un drop-in temporal con `ASP_SANDBOX_IDLE_TIMEOUT`, `ASP_STOPPED_SANDBOX_TTL`, `ASP_MAX_STOPPED_PER_TENANT`, `ASP_RETENTION_SWEEP`, `ASP_NODE_STALE_AFTER`, `ASP_NODE_FAILOVER_AFTER` y `ASP_NODE_MONITOR_INTERVAL` (el intervalo ha de ser menor que la ventana de `stale`); después, quitarlo.
- **Un nodo perdido**: `sudo kill -STOP <pid del node-agent>` y luego `-CONT`.
- Dentro del guest **no hay DNS** (el egress es deny-by-default), así que `apt` no instala nada: se deja un `.deb` en el workspace y se hace `dpkg -i`.
- Por SSH, `asp session exec` reenvía la entrada estándar: dale `< /dev/null` o se come el resto de un `bash -s`.
